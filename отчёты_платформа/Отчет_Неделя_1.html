Блок 1: Экономическое обоснование проблемы и формализованные метрики

Problem & Economics

1.1. Макроэкономическая стоимость легаси-кода и цена инженерной неэффективности

Современная индустрия разработки программного обеспечения столкнулась с системным кризисом сопровождения устаревших кодовых баз. Вопреки популярному представлению о том, что основное время инженеров уходит на создание новой бизнес-функциональности, реальные эмпирические данные ведущих мировых аналитических институтов свидетельствуют об обратном:

Отчёт Stripe: «The Developer Coefficient» (2018)

Согласно глобальному исследованию компании Stripe [Stripe, 2018], мировая экономика теряет свыше $300 млрд ежегодно из-за неэффективности разработчиков, вызванной плохим кодом и техническим долгом:

  • Разработчики тратят в среднем 17.3 часа в неделю (более 42% рабочего времени) на обслуживание существующего кода, отладку, рефакторинг и исправление багов.
  • Непосредственно на борьбу с техническим долгом уходит 13.5 часов в неделю (33% всей инженерной ёмкости компании).
  • Ликвидация барьеров неэффективности способна увеличить глобальный ВВП на $3 трлн в течение десятилетия.

Исследования Gartner и Standish Group

Аналитические отчёты Gartner по модернизации корпоративных приложений [Gartner, 2023] и статистика Standish Group CHAOS Report фиксируют катастрофическую статистику классических переписываний систем:

  • Более 70% проектов модернизации и миграции легаси-систем терпят неудачу: срывают сроки, превышают бюджет или не достигают целевых бизнес-метрик.
  • От 60% до 80% всего IT-бюджета корпоративного сектора тратится исключительно на поддержание работоспособности устаревших систем («keeping the lights on»).
  • Попытки полного ручного переписывания кодовой базы с нуля («rewrite from scratch») имеют вероятность провала свыше 60% из-за потери скрытых контекстов и неявных инвариантов.

1.2. Почему именно миграция на Python и межрепозиторный синтез?

В рамках ВКР я фокусирую исследование на задаче автоматизированного переноса кодовых баз на Python и слияния независимых репозиториев. Актуальность и критичность именно этой пары задач обусловлены следующими факторами:

  1. Python как монопольный рантайм искусственного интеллекта: По данным отчётов GitHub State of the Octoverse (2024) и рейтингов TIOBE, Python занимает первое место в мире по популярности. Весь современный стек глубокого обучения, агентов, ML-инференса и научной обработки данных (PyTorch, Hugging Face, vLLM, LangChain) существует исключительно вокруг экосистемы Python. При этом миллионы строк критического бэкенд-кода корпораций написаны на PHP, Java, Ruby или C++. Компании не могут интегрировать современные ИИ-контуры в свои продукты, пока их утилиты и модели данных физически разделены языковым барьером.
  2. Проблема семантической фрагментации микросервисов (Multi-Repo Hell): В эпоху бума микросервисов компании раздробили кодовые базы на десятки изолированных репозиториев. Сегодня тренд развернулся в сторону модульных монолитов (Shopify, Basecamp, Uber) из-за колоссальных накладных расходов на рассинхронизацию контрактов API. Ручное слияние двух репозиториев требует сотен часов рутинной работы: разрешения конфликтов импортов, устранения дублирования утилит, унификации схем валидации (например, Pydantic) и сквозного переписывания тестов.

1.3. Формализованные метрики оценки эффективности ($K_1$–$K_9$)

Для исключения субъективных оценок «код выглядит хорошо», я разработал систему из 9 детерминированных метрик качества, разделенных на функциональные, архитектурные и экономические:

ID Метрика Математическая формула Интерпретация и целевое значение
K1 Semantic Compilation Rate $$K_1 = rac{N_{\text{valid\_ast}}}{N_{\text{total\_files}}} \times 100\%$$ Доля сгенерированных целевых файлов, проходящих валидацию парсером Tree-sitter и ast.parse() без синтаксических ошибок. Цель: 100%.
K2 Test Suite Retention Rate $$K_2 = rac{T_{\text{pass\_target}}}{T_{\text{pass\_source}}} \times 100\%$$ Отношение числа успешно пройденных unit/integration тестов в целевом репозитории (pytest) к числу тестов в исходном. Отражает сохранение бизнес-логики. Цель: ≥ 90%.
K3 Branch Coverage Equivalence $$K_3 = \frac{\text{Cov}_{\text{target}}}{\text{Cov}_{\text{source}}} \times 100\%$$ Сохранение покрытия ветвлений кода (branch coverage). Гарантирует отсутствие удаленных неявных краевых условий при миграции. Цель: ≥ 95%.
K4 Type Safety Index $$K_4 = 1 - \frac{E_{\text{mypy}}}{L_{\text{total}} / 1000}$$ Плотность ошибок строгой статической типизации (mypy / pyright) на 1000 строк кода. Гарантирует корректность Pydantic/Type Hints аннотаций. Цель: ≥ 0.98.
K5 Cyclomatic Complexity Stability $$K_5 = \left| 1 - \frac{M_{\text{target}}}{M_{\text{source}}} \right|$$ Дельта цикломатической сложности МакКейба (McCabe Complexity). Показывает, не превратил ли агент код в «лапшу» из вложенных if-else. Цель: ≤ 0.15.
K6 Cross-Repo Unification Ratio $$K_6 = 1 - \frac{D_{\text{post}}}{D_{\text{pre}}}$$ Коэффициент устранения дублирования кода при слиянии репозиториев (выделение общих утилит в shared-модуль). Измеряется токенизированным AST-сравнением. Цель: > 0.25.
K7 Self-Correction Efficiency $$K_7 = \frac{N_{\text{resolved\_errors}}}{N_{\text{sandbox\_errors}}} \times 100\%$$ Доля ошибок песочницы (traceback, compilation error), успешно устраненных субагентами без участия человека в замкнутом цикле рефлексии. Цель: ≥ 75%.
K8 Token Cost per Converted LoC $$K_8 = \frac{\sum \text{Tokens}_{\text{in}} \times P_{\text{in}} + \sum \text{Tokens}_{\text{out}} \times P_{\text{out}}}{L_{\text{migrated}}}$$ Экономическая эффективность: стоимость в долларах США на 1000 успешно мигрированных строк кода с учетом оверхеда субагентов. Цель: ≤ $0.08 / KLoC.
K9 Human Intervention Time Saved $$K_9 = 1 - \frac{t_{\text{review}} + t_{\text{manual\_fix}}}{t_{\text{manual\_migration\_baseline}}}$$ Экономия времени ведущего инженера-архитектора по сравнению с эталонным ручным переносом. Цель: ≥ 80%.

1. Claude Code (Anthropic)

CLI Autonomous Agent

Описание: Официальный терминальный агент компании Anthropic, запущенный в 2025 году для автономного выполнения задач в локальных репозиториях [Anthropic Docs, 2025].

  • Инструменты агента (Tools): Встроенный набор низкоуровневых операций: Read (чтение файла), Edit (точечный str_replace патчинг), Write (создание файла), Grep (поиск регулярных выражений), Glob (поиск по маске), Bash (выполнение shell-команд), Agent (спавн субагента для изолированной подзадачи), AskUserQuestion, WebFetch, WebSearch. Поддерживает протокол MCP (Model Context Protocol) для подключения внешних инструментов.
  • Устройство Harness: Терминальный цикл ReAct с контекстным сжатием (compaction). Проектные инструкции считываются из стоячего файла CLAUDE.md в корне репозитория. Для тяжелых задач планирования агент порождает дочерние контексты Plan и Explore.
  • Модель разрешений (Permissions): Трёхуровневая: Manual Mode (запрос одобрения на каждую модификацию файла и сетевой вызов), Auto Mode (встроенный классификатор безопасности автоматически одобряет безопасные действия), Bypass Mode (флаг --allow-dangerously-skip-permissions). Белый список команд настраивается в файле .claude/settings.local.json. Безопасные команды чтения (git status, git diff) разрешены по умолчанию.
  • Песочница (Sandbox): По умолчанию исполняется прямо в терминале пользователя под правами текущей сессии с перехватом команд через whitelist/blacklist. Корпоративный запуск изолируется через внешний Docker-контейнер.
  • Источник и уровень доказательности: Официальная документация Anthropic Docs [URL] (Level 3 Evidence: Vendor Specs); анализ утёкших системных промптов в репозитории Piebald-AI/claude-code-system-prompts [GitHub] (Level 4 Evidence: Reverse-Engineering).

2. Cursor Agent / Composer (Anysphere)

IDE Multi-File Agent

Описание: Интегрированная среда разработки нового поколения на базе VS Code, использующая фоновый мульти-файловый агент Composer [Cursor Docs, 2024].

  • Инструменты агента (Tools): codebase_search (локальный эмбеддинг-поиск по векторизованному репозиторию), read_file (чанковое чтение ~250 строк), edit_file (генерация структурированных diff-блоков), terminal_run (выполнение bash-скриптов с перехватом stdout/stderr), @docs индексатор.
  • Устройство Harness: Полнодуплексный стейт-машинный цикл. Контекст непрерывно насыщается активными файлами редактора, положением курсора, историей правок и диагностикой LSP (Language Server Protocol). Для поддержания фокуса вставляются скрытые системные блоки <system_reminder>.
  • Модель разрешений (Permissions): Изменения в коде представляются пользователю в виде диффов прямо в окне редактора с кнопками Accept / Reject (построчно или для всего файла). Запуск терминальных команд требует подтверждения, если не включен авто-режим.
  • Песочница (Sandbox) — Shadow Workspace: Уникальная архитектурная особенность Cursor — концепция теневого рабочего пространства (Shadow Workspace). При глубоком рефакторинге модификации сначала применяются к виртуальной in-memory копии файлов. Фоновый процесс запускает линтеры и тайпчекеры (LSP) против теневого состояния. Если агент сломал типы или синтаксис, ошибка возвращается в модель до того, как пользователь увидит сломанный diff на диске.
  • Источник и уровень доказательности: Официальная документация Cursor Docs [URL] (Level 3 Evidence); технический разбор теневого воркспейса [Tianpan, 2024] (Level 2 Evidence); дампы промптов в x1xhlol/system-prompts-and-models-of-ai-tools [GitHub] (Level 4 Evidence).

2.4. Сравнительный GAP-анализ (Матрица нерешённых проблем)

Я категорически отказываюсь от антинаучного вывода «у проекта нет аналогов». Напротив, современные коммерческие и академические агенты демонстрируют выдающиеся результаты в точечном исправлении ошибок (Bug Fixing на SWE-bench). Однако проведённый аудит выявляет фундаментальный архитектурный разрыв (GAP) между существующими решениями и задачами переноса кодовых баз и межрепозиторного слияния:

Критерий сравнения SWE-agent / OpenHands Claude Code / Cursor Devin / Google Jules Наш Repo-Harness (Целевой)
Основной фокус Локальный Bug Fixing (1–3 файла в SWE-bench) Парное программирование и рефакторинг в IDE/CLI Автономные тикеты и закрытие GitHub Issue Масштабный перенос языка и слияние репозиториев
Удержание графа зависимостей Отсутствует (плоский поиск по файлам) Локальный векторный поиск по чанкам (RAG) Файловый контекст сессии Сквозной типизированный граф (Tree-sitter + NetworkX)
Трансляция языковых парадигм Не поддерживается (работа внутри одного языка) Построчная текстовая конвертация (галлюцинации типов) Ограничена единичными скриптами Синтаксический мэппинг типов (Pydantic / Type Hints)
Межрепозиторный синтез (Multi-Repo) Только один репозиторий в рабочей директории Только одно рабочее пространство Один репозиторий на виртуальную машину Одновременная оркестрация N репозиториев
Верификация инвариантов Только запуск существующих тестов Теневой линтинг (LSP) Запуск CI/CD пайплайна Сравнение AST-инвариантов и Branch Coverage Equivalence

Главный вывод GAP-анализа: Ни одна из существующих систем не обладает специализированным исполнительным контуром для межъязыковой трансляции архитектур и дедупликации нескольких кодовых баз. Они либо захлёбываются в контексте при попытке охватить десятки файлов сразу, либо генерируют синтаксически правдоподобный, но архитектурно неработоспособный код без сохранения семантических инвариантов.

8 Reflection & Self-Correction Loop Парсинг ошибок компилятора, линтера и тестов из песочницы, очистка от шума и формирование целевого промпта для исправления кода субагентами. Корректирующий контекстный патч для повторной генерации.

В процессе интеграции я столкнулся с инженерной проблемой: на хост-машине Windows активен VPN-клиент (AmneziaVPN), который перехватывал сетевые интерфейсы и блокировал лупбек-запросы из WSL2 на порт 11434. Я решил эту проблему архитектурно:

  1. Создал системный фоновый сервис scripts/ollama-proxy.service (systemd), слушающий порт 11435 в Linux и транслирующий вызовы в хостовый инференс.
  2. Создал системный CLI-враппер /usr/local/bin/ollama, позволяющий вызывать консольные команды ollama list, ollama ps прямо из терминала Linux.
  3. Написал автоматический тестовый набор tests/test_ollama.py, подтвердивший 100% работоспособность инференса (Pytest 2/2 пройдены за 1.65 секунды с загрузкой qwen2.5:7b в 100% VRAM GPU).

6.1. Графовое хранилище знаний (Code-RAG)

Я обосновал отказ от наивного текстового RAG (разделение кода на текстовые чанки по 500 токенов и векторный поиск). Для инженерных задач миграции текстовый RAG губителен, так как разрывает семантические связи между определением метода и местом его вызова. Вместо этого в Repo-Harness спроектировано графовое хранилище знаний (Graph Code-RAG):

  • Синтаксический уровень: Локальный индекс Tree-sitter хранит точные координаты AST-узлов (классы, методы, параметры, типы).
  • Семантический уровень: Граф вызовов NetworkX позволяет извлекать контекст «снизу вверх»: при переносе конкретной функции агент получает в контекст не случайный соседний текст, а точные сигнатуры всех вызываемых ею зависимостей.
  • Каталог навыков (/skills): Библиотека проверенных правил трансляции (соответствие методов Array.prototype.map → list comprehensions в Python, сопоставление декораторов @Injectable → dependency injection паттернам).

Блок 7: Детальная спецификация первой функциональности (Feature №1)

First Feature Spec

7.1. Название и архитектурная роль фичи

Фича №1: Многоязычный синтаксический экстрактор и построитель графа зависимостей (Repo-Mapper & AST Extractor).

Почему именно она выбрана первой: Ни один субагент не способен корректно перенести хотя бы одну строчку кода, пока не решена фундаментальная проблема упорядочивания: в каком порядке компилировать модули? Попытка случайного переноса приводит к каскадным ошибкам ModuleNotFoundError и NameError. Фича №1 закладывает строгий детерминированный фундамент: строит топологический порядок миграции (от листьев дерева зависимостей к корню).

7.2. Архитектурная схема работы модуля

flowchart LR
    Files["Файлы репозитория (*.ts, *.js, *.py)"] --> Parser["Tree-sitter Parser Engine"]
    Parser --> AST["Синтаксические деревья (AST Nodes)"]
    AST --> Extractor["Сборщик метаданных:
• Экспорт функций/классов
• Импорты и внешние вызовы
• Аннотации типов"]
    Extractor --> GraphEngine["NetworkX DiGraph Constructor"]
    GraphEngine --> TopoSort["Алгоритм топологической сортировки
(Kahn's Algorithm / Cycle Resolver)"]
    TopoSort --> Output["Pydantic Dependency Graph JSON
(Очередь задач миграции L1 -> L2 -> L3)"]
