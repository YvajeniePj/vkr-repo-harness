1 Погружение в проблему и метрики

Реальная индустриальная проблема

В качестве темы своего исследования я выбрал миграцию унаследованного программного обеспечения (Legacy Modernization) и обратный инжиниринг кодовых баз. Это одни из наиболее ресурсоемких и дорогих процессов в IT-индустрии. Корпоративный перенос крупной системы с устаревших или разнородных языков (JavaScript/TypeScript, C++, Go) на унифицированный целевой стек (Python) занимает у команд инженеров от 6 до 18 месяцев и сопряжен с огромными бюджетами.

Аналогичный вызов возникает при необходимости слияния двух независимых продуктов (мой референсный сценарий: интеграция графового пайплайна генеративных моделей ComfyUI в систему оркестрации сценариев n8n). Инженеру приходится вручную изучать архитектуру обеих систем, согласовывать структуры данных и переписывать стыковочные узлы, что требует сотен часов ручной работы.

Почему «голая» LLM не решает задачу

В ходе предварительного анализа я выделил 4 фундаментальные причины, почему обычный вызов языковой модели не справляется с репозиториями:

  • Эффект «Lost in the Middle» и деградация внимания: Даже при окне контекста в 1–2 миллиона токенов загрузка десятков файлов приводит к потере зависимостей, пропуску граничных условий и галлюцинациям в сигнатурах методов.
  • Хрупкость генерации файлов (Patch Failure): Принуждение модели переписывать файлы целиком приводит к астрономическому расходу токенов и случайному стиранию критического функционала. Традиционные patch-диффы ломаются при малейшем расхождении номеров строк.
  • Отсутствие исполнительного контура: Модель не видит синтаксических ошибок, падений тестов и регрессий в реальном времени. Без песочницы обратная связь сводится к догадкам.
  • Неконтролируемая стоимость: Использование frontier-моделей (GPT-4o, Claude 3.5 Sonnet, Gemini Pro) для рутинных операций (сбор дерева файлов, поиск импортов) делает процесс экономически нецелесообразным.

Что меняет Repo-Harness в моем подходе

Я проектирую Repo-Harness как систему, которая превращает LLM из текстового генератора в управляемый компилятор проектов, предоставляя: (1) изолированную песочницу под Linux с валидацией запусков, (2) сжатое AST-дерево вместо гигабайтов сырого кода, (3) двухуровневую маршрутизацию между дорогими и дешевыми моделями, и (4) детерминированный движок применения и отката правок.

Измеряемые показатели качества (KPI K1–K9)

Для объективной оценки результатов своей системы я зафиксировал 9 формальных метрик:

K1. Успешный запуск (Clean Health Check)

K1 = Passed_Runs / Total_Runs

Доля попыток, где результат устанавливается в чистом изолированном контейнере одной командой и проходит проверку работоспособности.

K2. Функциональная полнота

K2 = α · Tests_Ported + (1 - α) · Tests_Diff

Доля пройденных портированных тестов оригинала и дифференциальных тестов (совпадение выходов при одинаковых входах).

K3. Интегральный успех задачи

K3 = 1 ⇔ (K1 == 1) AND (K2 ≥ 90%)

Бинарный критерий: система запустилась и покрыла не менее 90% верификационных сценариев.

K4. Стоимость задачи ($)

C_success = ∑Cost / Count(K3 == 1)

Средние долларовые затраты на успешный результат через LiteLLM Proxy по фиксированным тарифам.

K5. Токены на 1 kLOC

Tokens_Norm = Total_Tokens / (LOC_src / 1000)

Удельный расход входных, выходных и кэшированных токенов на каждую 1000 строк исходного репозитория.

K6–K9. Автономность и надежность

K6: Общее время и число шагов агента.
K7: Доля прогонов без ручного вмешательства человека.
K8: Доля успешно применившихся патчей и чистых откатов.
K9: Стандартное отклонение и 95% bootstrap CI между 3+ прогонами.

2 Анализ существующих решений на мировом рынке

В ходе аналитического исследования рынка я детально изучил архитектуру и опыт 6 ключевых агентных систем для разработки ПО:

1. SWE-agent (Princeton University)

Суть: Использует специализированный Agent-Computer Interface (ACI), позволяющий модели просматривать файлы окнами по 100 строк, искать вхождения символов и редактировать диапазоны.

Ограничения: Заточен строго на локализацию одиночных багов в рамках существующих Python-репозиториев (бенчмарк SWE-bench). Не поддерживает глобальный рефакторинг, кросс-языковой перенос и слияние независимых проектов.

2. OpenHands (ex-OpenDevin)

Суть: Открытая многоагентная платформа, запускающая Docker-песочницу с bash-интерфейсом и браузером.

Ограничения: Высокая частота галлюцинаций при работе с большими кодовыми базами (>20k LOC); отсутствует структурное кэширование AST-дерева; нет маршрутизации между моделями разного уровня интеллекта.

3. Aider (Paul Gauthier)

Суть: Консольный инструмент парного программирования. Формирует компактную Repo Map на основе ctags/tree-sitter и применяет точечные search/replace блоки правок.

Ограничения: Предназначен исключительно для работы в режиме «Human-in-the-Loop» (интерактивный диалог). Не имеет автономной иерархии субагентов для непрерывной многочасовой миграции.

4. MetaGPT / ChatDev

Суть: Ролевая симуляция софтверной компании (Product Manager, Architect, Engineer, QA), передающих друг другу документы.

Ограничения: Модели способны генерировать только простые учебные скрипты «с нуля». Полностью не приспособлены к реверс-инжинирингу и анализу существующего сложного кода сторонних репозиториев.

Я спроектировал архитектуру Repo-Harness на принципах модульности, строгой безопасности и приоритета платформы **Linux**. Для выполнения требований ТЗ («Linux в первую очередь, поддержка Windows через WSL») среда исполнения песочницы изолируется внутри Linux-контейнеров и WSL2.

Детальная спецификация 8 модулей системы

Модуль Входные данные Выходные данные Ожидаемый результат и назначение
1. Sandbox (Linux) Команда, аргументы, рабочая директория Stdout, Stderr, Exit Code, CPU/RAM метрики Изолированное исполнение в Linux (WSL2/Docker), контроль путей (no path-traversal), белый список команд.
2. GitHub Read-Only URL репозитория, токен (в защищенном хранилище) Локальный клон рабочей ветки Безопасная загрузка без раскрытия учетных данных агентам; физический запрет push.
3. Tree Analyzer Файловое дерево репозитория AST-граф символов, Repo Map в Markdown Сворачивание служебных файлов (node_modules), извлечение классов, функций и импортов через Tree-sitter.
4. Context Manager Запросы субагентов на чтение файлов Отфильтрованный контекст с кэшированием Динамическая выгрузка неиспользуемых файлов, сжатие истории диалога, Context Caching.
5. Orchestrator Глобальная цель (перенос / слияние) План задач, вызовы субагентов, слияние Иерархическая координация работы, предотвращение зацикливаний, валидация результатов.
6. LLM Router Подзадача субагента Назначение на L1 (Frontier) или L2 (Fast) Экономия бюджета: рутина уходит быстрым моделям, сложный дебаг — топ-моделям.
7. Patch Engine Блоки Search/Replace либо Git-патчи Модифицированный файл или Clean Rollback Сравнение надежности двух подходов правок кода без переписывания целых файлов.
8. Vue UI Пользовательский ввод, архивы .zip Интерактивный экран, трассировка шагов Локальный веб-интерфейс с возможностью визуального аудита действий агентов.

6 Хранилище знаний и синтаксический анализ (Tree-sitter AST)

Почему я отказался от векторного RAG для кода

Классический векторный RAG (сегментация на чанки по 500 символов и поиск по косинусному расстоянию эмбеддингов) катастрофически неэффективен при анализе архитектуры. Исходный код — это строго типизированный ориентированный граф, где разрыв тела функции или потеря строки импорта делает контекст бесполезным.

Мое решение: Символьный граф на базе Tree-sitter

Вместо векторизации для Repo-Harness я внедряю детерминированный статический парсер:

  • Извлечение синтаксического дерева: Для каждого файла на JS/TS/Go/Rust извлекаются AST-узлы классов, функций, интерфейсов и экспортов.
  • Формирование Repo Map: Генерируется компактное дерево зависимостей, отражающее взаимные вызовы между модулями (Call Graph).
  • Экономия контекста: Repo Map занимает всего 2–5% от объема сырых исходников, сохраняя для модели 100% архитектурной картины проекта.

7 Детальный разбор первой фичи (Старт разработки)

Выбранная первая фича: «Изолированная песочница (Sandbox под Linux) с AST Tree-sitter анализатором»

Обоснование моего выбора: Песочница и анализатор файлового дерева — это фундаментальный базис системы. Ни один субагент не может безопасно функционировать и принимать архитектурные решения без контролируемой среды выполнения команд и компактной карты кодовой базы.

Песочница строится в первую очередь для среды **Linux** (POSIX-процессы, таймауты, виртуальные окружения venv, управление правами доступа), что полностью соответствует требованиям технического задания.

Архитектура фичи

+--------------------------------------------------------------------------+ | FIRST FEATURE ARCHITECTURE PIPELINE | +--------------------------------------------------------------------------+ | Input: Directory Path (e.g. /workspace/repos/marked) | | | | [ Step 1: Security Validation in Linux Sandbox ] | | • Resolve realpath() & verify within session root | | • Reject symlinks pointing outside workspace | | | | [ Step 2: Tree Pruning ] | | • Filter out: .git, node_modules, .venv, dist, __pycache__ | | • Collapse binary assets: [images: 45 files (.png, .svg)] | | | | [ Step 3: Tree-sitter AST Extraction ] | | • Parse definitions: class, function, export, import | | • Build symbols index (Symbol -> File -> Line Range) | | | | [ Step 4: Output Generation ] | | • JSON Schema: { "modules": [...], "dependencies": [...] } | | • Markdown Repo Map for Model Prompt Context | +--------------------------------------------------------------------------+

Спецификация интерфейса (Контракт)

  • Входные данные: repo_path: Path, allowed_commands: list[str].
  • Выходные данные: Структурированный JSON с деревом символов и markdown-текст карты репозитория.
  • Меры безопасности: Принудительный таймаут исполнения (120 сек), лимит памяти процесса (4 GB), изоляция переменных окружения (токены GitHub не экспортируются в дочерние процессы).
